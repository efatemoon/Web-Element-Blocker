## web-element-blocker.user.js iframe 防线修复（v3.3.0）
- 用户 4 项反馈：① 白名单完全无效→删除 ② 深度扫描/重新扫描混淆→厘清 ③ 拦截后刷新复活→持久化 ④ iframe 规则未进「管理规则与防御策略」→打通统一管理
- 根因：
  - 白名单无效：`ProtectedCheck.isProtected`（真实隐藏守卫）从不查 `WhitelistStore`；面板手动拦截直穿 `BlockEngine.hideElement`；`rec.manual` 仅存 WeakMap 刷新即失。白名单只在 `ContentClassifier.classify` 自动路径生效，对手动拦截/刷新重扫无约束力
  - 拦截不持久：帧级「拦截选中」只做内存 `BlockEngine.hideElement` + `rec.blocked=true`，未写 `iframeBlock` 规则 → 刷新丢失、也不进管理面板
  - 深度/重新扫描：仅「重新扫描」调 `forceRescan()`，两者都绕过 5s 缓存，行为重叠文案无差
- 修复：
  - 彻底删除 `WhitelistStore` 模块及全部引用（classify 分支、_classifyAndAct 粘性判定、protectInFrame、IframePanel 白名单 UI/renderWlList/btn-protect-iframe、storage export/import iframeWhitelist 桶、AdGuard 导出 @@白名单段）
  - 帧级拦截对跨域 iframe 写持久 `iframeBlock` 规则（`storage.addIframeRule({matchType:'srcDomain', value: hostname})`）→ 刷新自动拦截 + 管理面板 `getIframeBlocks()` 以 `iframeBlock` 类型统一管理（删除/禁用走 removeIframeRule/toggleIframeRuleDisabled + rescanAll）
  - 深度扫描 = 重新扫描 + 临时拉满嵌套深度 + 强制重跑帧内元素级深扫；重新扫描 = forceRescan + 重新分类；按钮加 tooltip 厘清差异
- 局限：跨域帧内元素级受浏览器同源策略只能内存隐藏（刷新由该 iframe src 域名的 iframeBlock 规则兜底）；旧 `iframeWhitelist` GM 数据不再读取可遗留
- 版本：user.js + meta.js `3.2.0` → **3.3.0**
- 验证：node --check ✅；npx jest ✅ 16 套件/**76 用例**全绿（新增 3 个 v8.6 回归守卫）

## web-element-blocker.user.js 架构/功能代码复审与隐藏 bug 修复（v3.4.2）
- 复审背景：用户要求用 review-and-refactor + javascript-testing-patterns 对架构与功能代码审查、解决隐藏 bug。
- 基线：v3.4.1 已提交本地（node --check ✅ / jest 17 套件 81 用例绿）。
- 发现并修复 2 个隐藏 bug（均非用户直接报告，但影响正确性/性能）：
  1. **点击拦截器误删正常 UI 的护栏失效**（Bug A）：v3.4.1 引入的 `_isAdOverlayContainer` 护栏基于 `VICE_CONTAINER_RE`（含 overlay|modal|mask|cover|layer 等通用框架词），`.el-overlay`/`.el-drawer` 仍判 true → `container.remove()` 仍会整块误删 Element-Plus 弹窗。**修复**：全局 click 处理器彻底移除 `container.remove()` 与 `_isAdOverlayContainer`，只保留 `preventDefault`/`stopPropagation` 跳转拦截；DOM 隐藏交由覆盖层扫描引擎（透明门控 autoBlock）统一处理。结构上根除「正常元素点击后消失」。
  2. **debounce 首帧同步触发**（Bug B）：`debounce(func,wait,maxWait)` 原 `lastExec=0`，首帧 `now-0>=maxWait` 恒成立 → MutationObserver 首帧同步执行重扫，破坏去抖语义 + 首屏卡顿。**修复**：`lastExec=null`，仅 `lastExec!==null && now-lastExec>=maxWait` 才立即触发，首次必走 `setTimeout(wait)`；maxWait 兜底语义保留。唯一使用方 `DomScanner.startObserver` 的 `debouncedDynamicApply(120,600)`。

## web-element-blocker.user.js 复杂规则条件求值隐藏 bug 修复（v3.4.3）
- 复审背景：延续 v3.4.2 的 review-and-refactor + javascript-testing-patterns 复审，对 `RegexEngine.evaluateConditions`（积木/complex 规则条件求值核心，user.js L1753）做字面语义级审查。
- 发现并修复 2 个隐藏正确性 bug（均非用户直接报告，静默导致复杂规则漏匹配/误匹配）；均已用 `new Function` 抽取**真实源码**做回归 + 旧版本反向验证确认非假阳性：
  1. **FIX-A（not_contains 空值误判）**：text/id 分支原 `return val !== '' && !val.includes(c.value)`，空文本/属性时 `val!==''` 为 false 短路返回 false；语义上「不含 X」对空值应恒真。**后果**：含 `not_contains` 的 AND 规则遇空值元素整条漏匹配、元素未被屏蔽。**修复**：统一 `return !val.includes(c.value)`（空值 → true 正确）。
  2. **FIX-C（class equals 整串比较）**：class 分支原 `val.trim() === c.value.trim()`，`val` 是整串 className（如 `"header nav"`），而规则 value 多为单 class（如 `"header"`）→ 多 class 元素永远不匹配。**后果**：`class equals header` 对真实多 class 元素一律失效，contains/not_contains 边界也不确定。**修复**：按独立 class 词元匹配（`className.trim().split(/\s+/)`，`equals`→`tokens.indexOf(value)!==-1`，contains/not_contains→`tokens.some(t=>t.includes(value))`），与 `SelectorBuilder.generateOptimalSelector` 口径一致。
- 新增回归测试：ad-block-test/complex-rule-logic.test.js（extractMethod + new Function 抽取真实源码求值，10 项断言全绿：FIX-A 4 项 + FIX-C 6 项）。
- 验证：node --check ✅；旧 v3.4.2 复现 4 用例全返错误结果确认确为 bug；jest **19 套件 / 95 用例全绿**（18→19 套件，85→95 用例）。
- 版本：user.js + meta.js `3.4.2` → **3.4.3**。
- 报告：ad-block-test/ARCH_OPTIMIZE_REPORT.md 新增第十一节（v3.4.3 隐藏 bug 复审）、第十节版本刷新为 3.4.3。
