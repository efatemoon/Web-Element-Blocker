## web-element-blocker.user.js 管理面板「删除撤销」修复（UI 交互缺陷）

### 用户报告
管理面板删除规则后「没有撤销功能 / 奇怪错误提示」。

### 实测结论
撤销功能**已实现**（`showManager → ManagerPanel.call(this) → UIManager._pushUndo/_restoreEntry` 链路完整），但存在致命交互缺陷：
- 旧 `_performUndo()` 用 `this._undoStack.pop()`（全局 LIFO 栈），而每条删除 Toast 按时间顺序弹出。
- 删除 A → 删除 B 后，点击 A 的 Toast「撤销」会弹出栈顶=B，**恢复错误规则** → 用户感知「撤销是假的」。

### 修复（方法级，未拆分文件）
1. `_pushUndo(entry)` 现返回该条目。
2. 删除全局 LIFO 的 `_performUndo()`，新增 `_restoreEntry(entry)`：每条 Toast 绑定**自身**删除条目，精确恢复 + `_restored` 幂等保护。
3. 单条/批量删除原本各自重复「iframeBlock>global>current>other」三分支快照捕获，统一抽取为 `_captureDeletedRule(scope,domain,type,index)`，消除 ~20 行重复。
4. Toast 文案明确「5 秒内可撤销」，撤销成功回显「已撤销删除」。

### 审查发现
- 全仓删除操作 100% 集中在 `ManagerPanel`（唯一 `btn-delete` 与全部 `removeRule*`/`removeIframeRule` 调用）→ 其余 8 个面板无删除面，不受同类缺陷影响。
- 无原生 alert/confirm/prompt（全 Toast 化）。
- `clearPanel()` 已正确退订 EventBus、停选择模式、还原预览，无监听器泄漏。

### 验证
- `node --check` → SYNTAX_OK
- `jest` → 20 suite / 100 test 全通过（含 menu-wiring / PanelRegistry 9 面板分派）

### 交付物
- 报告：`manager-undo-fix-report.html`（架构图 + 删除/撤销时序图 BEFORE/After + 9 面板审查表）

## web-element-blocker.user.js iframe 防线元素拦截修复

### 用户报告（截图）
1. iframe 防线面板检测的是 iframe 本身，用户要的是帧内广告元素。
2. 无法全选广告元素。
3. 元素拦截后刷新界面又出现，不确定是否拦截成功。

### 根因
- **P0：元素级规则未持久化** — `IframeGuard.blockInFrameNode` 使用 `this.storage`，但 `IframeGuard` 未注入 storage 引用 → `addRuleForDomain` 抛异常被静默 catch，规则根本没写进去。
- **P0：刷新后未自动应用规则** — `reapplyInFrames()` 只在管理面板规则启用/禁用时调用，`init()` 没有在页面加载时应用已保存的帧内规则。
- **P1：深扫 pathPattern 分支失效** — `IframeDeepScanner.scanFrame` 同样 `this.storage` undefined。
- **P1：选择器过宽** — `_buildSelector` 生成 `img` 等过宽选择器，且 `blockInFrameNode` 因已有 selector 跳过 `generateOptimalSelector`。
- **P1：预览对 iframe 内元素无效** — `document.contains(el)` 只认顶层文档。
- **P1：递归嵌套 iframe record 指向父帧** — `scanFrame` 递归调用传错 iframe 参数。
- **UI：默认勾选 iframe 容器** — `runScan` 对 frame 类型也执行 highRisk 默认勾选。
- **UI：缺少全选按钮** — 只有「选中高风险/清空」。

### 修复
1. `IframeGuard.storage = StorageService;` / `IframeDeepScanner.storage = StorageService;`
2. `IframeGuard.init()` 末尾调用 `reapplyInFrames()`。
3. `_scanContentIframe()` 域名封杀后调用 `_applyRulesToDoc(doc, host)`。
4. 抽取 `_applyRulesToDoc(doc, host)` 供 `reapplyInFrames` 与 `_scanContentIframe` 复用。
5. `_buildSelector` / `_buildRecord` / `blockInFrameNode` 统一优先使用 `generateOptimalSelector`。
6. `IframePanel`：默认只勾选 element 类型；新增「全选当前」按钮；`collectAll` 对 `display:none` 元素显示「已拦截」；Toast 明确提示规则已保存。
7. `updatePreview` 改用 `el.isConnected`。
8. 递归扫描嵌套 iframe 修正为传入 `inner`。

### 隐藏 Bug 检查
- 检查了 EventBus 订阅清理（`clearPanel` 已正确处理 `_iframePreview` 与 `_iframeUnsubs`）。
- 检查了 preview state 跨面板泄漏（`clearPanel` 会还原）。
- 未发现其他同类 UI 交互缺陷。

### 验证
- `node --check` → SYNTAX_OK
- `jest` → 20 suite / 100 test 全通过

### 交付物
- 报告：`iframe-defense-fix-report.html`（架构图 + 元素拦截持久化流程图 + Bug 清单 + 用户操作说明）

## web-element-blocker.user.js 全架构审计 + 隐藏 Bug 修复（9 面板）

### 范围
按 MENU_ITEMS 9 项梳理整体架构（入口→UIManager 协调器→9 面板函数→服务端口层 StorageService/DomainBlockExecutor/RuleDomain/OverlayService/EventBus→引擎层 BlockEngine/IframeGuard+FrameDetector/OverlayScanEngine+GDS/SelectorBuilder/GlobalDomainScanner→StorageManager→页面 DOM）。PanelRegistry 为 OCP 接缝，StorageService 为 Proxy 写入端口，DIP 服务层。

### 本轮新增修复
- **Bug-X1 (HIGH) iframe 选择监听泄漏**：`_handleClick` 进入同源 iframe 时在 `iframe.contentDocument` 注册 9 个 capture 监听，但原 `stopSelection→_untrackDocAll` 只注销主文档监听，导致帧内点击被永久 `preventDefault` 拦截 + 重复进入累积监听。修复：新增 `_trackDocOn(doc,type,handler,opts)`，`_untrackDocAll` 按 entry.doc 注销（addEventListener 自动去重防累积）。
- **Bug-X2 (MED) 覆盖层重扫清空勾选**：`runScan` 重扫前记录已勾选元素引用，扫描后 `findIndex(r=>r.el===el)` 回填 `selectedSet`，避免「重新扫描/深度扫描」丢失人工勾选。
- **Bug-X3 (LOW) 域名大小写漏过滤**：`GlobalDomainPanel` 读取已封杀域名统一 `.toLowerCase()`（3 处），防「已封杀域名」又出现在可选列表。

### 审查结论
- 其余面板（selection/regex/domain/overlay/manager/iframe/export/adguard/import）无额外隐藏交互/逻辑 Bug（manager undo、iframe 持久化已在前序修复）。
- `clearPanel()` 统一 stopSelection + 还原全部预览 + 退订 EventBus，无监听器泄漏。

### 验证
- `node --check` → SYNTAX_OK；`jest` → 20 suite / 100 test 全通过。
